## 1. Мета проєкту

Побудувати **один продукт, який одночасно закриває дві лаби**:

- **Lab 01** — «Mini Messenger»: користувачі, розмови, повідомлення, персистентне сховище, валідація. Цільовий рівень: **Advanced** (client-server, автентифікація, статуси, edit/delete з історією, групи, web UI).
- **Lab 21** — «REST API with Real Auth»: REST API, хешовані паролі, токени, per-user доступ, OpenAPI, деплой. Цільовий рівень: **Advanced** (rate limiting, RBAC, password reset, пагінація, structured logging, тести, CI/CD).

Спільна ідея: месенджер **і є** Lab 21-бекендом (домен = чати), а React-клієнт — «Lab 22» із розділу *Extension challenges*, а SignalR — «Lab 23».

## 2. Короткий підсумок аналізу вашого попереднього плану

**Загальний висновок:** план дуже сильний і за глибиною *перевищує* Advanced-рівні обох лаб. Лаби формулюють Advanced як «додайте щось із переліку» — у вас майже все з переліку вже є. Проблема не в нестачі функціоналу, а в трьох речах:

1. **Випали «нудні» пункти рубрики**, які рекрутер/викладач перевіряє першими: пошук по повідомленнях (обов’язковий для Lab 01 Standard!), OpenAPI-документація на `/docs`, `/health`, rate limiting, тести + CI/CD, structured logging, формат помилок (422/ProblemDetails), «Make it yours» (обов’язковий твіст), README/демо-артефакти.
2. **Є архітектурні ризики**, які зламають деплой або коректність, якщо їх не вирішити зараз (розд. 5): cross-site cookie для refresh при Vercel + окремий бекенд; SQL Server і «повністю безкоштовний» хостинг; порядок commit’ів у `Sequence`; MediatR змінив ліцензію.
3. **Обсяг.** Лаби розраховані на ~2 + 2 тижні (≈30–45 год на кожну). Ваш перелік — це ~150–190 год соло. Тому в плані (файл 2) є чіткі **cut lines**: що обов’язково, а що можна відкласти без втрати оцінки.

**Оцінка покриття:** Lab 01 — ≈90 % (немає пошуку, твісту, вкладень-метаданих); Lab 21 — ≈65 % (немає /docs, rate limit, тестів, CI/CD, logging, версіонування, системної RBAC, health).

Легенда: ✅ покрито · ⚠️ частково / потрібне уточнення · ❌ відсутнє · ➖ не потрібно

## 5. Ризики й проблемні місця у припущеннях (потрібні рішення)

| # | Тема | Проблема | Рекомендація |
|---|---|---|---|
| **P-01** | Refresh-cookie при Vercel + окремий бекенд | Frontend на `*.vercel.app`, API на `*.onrender.com` — це **cross-site**. HttpOnly-cookie доведеться ставити `SameSite=None`; браузери (Safari, дедалі більше Chrome) блокують third-party cookies → refresh ламається. Vercel також не проксіює WebSocket | **Same-origin деплой:** ASP.NET Core віддає зібраний React зі `wwwroot` в тому ж контейнері. Тоді `SameSite=Strict`, немає CORS, WebSocket працює. Vercel лишається як варіант B (потрібен спільний власний домен) |
| **P-02** | SQL Server і «повністю безкоштовно» | Безкоштовного SQL Server із постійним хостингом майже немає. Є Azure SQL free offer (потрібна Azure-підписка з карткою, ліміт 100 000 vCore-секунд/міс, авто-пауза) | Рекомендація: **PostgreSQL (Neon free)** — EF Core абстрагує провайдера; SQL Server залишити як варіант B. Рішення — OQ-01 |
| **P-03** | Порядок `Sequence` | Глобальний identity може **закомітитись не по порядку** (seq 10 після seq 11) → клієнт, що синхронізується `after=11`, назавжди пропустить 10 | Лічильник **per-conversation**: атомарний `UPDATE … SET last_sequence = last_sequence+1 … RETURNING` в тій самій транзакції; рядок розмови блокується → порядок commit = порядок sequence |
| **P-04** | MediatR | З v13 — dual license (безкоштовно для Community: <$5M виручки, навчання, non-production; потрібен license key). v12 — Apache 2.0 | Для лаби ок будь-що; рекомендація: **`Mediator` (source-generated, MIT)** або MediatR 12.x. API майже ідентичний |
| **P-05** | Domain Events | Якщо публікувати події *до* commit, клієнти отримають повідомлення, яке потім відкотилось | Збирати події в агрегатах, публікувати **після успішного `SaveChanges`** (interceptor). Збої обробників не відкочують дані. Апгрейд-шлях — Outbox |
| **P-06** | `ChatResetAt` / `JoinedAt` | Часові мітки крихкі (часові пояси, однакові мілісекунди) | Зберігати **вотермарки в sequence**: `VisibleFromSequence`, `ClearedUpToSequence` (+ timestamp для UI) |
| **P-07** | Статус у групах | «Delivered/Read» у групі неоднозначні | **Прийняте припущення:** агреговано для автора — Delivered, коли отримали *всі*; Read, коли прочитали *всі*; Message Info показує по кожному учаснику |
| **P-08** | Snapshot username | Формулювання «старі повідомлення зберігають старий username+DisplayName» стоїть у секції Deleted account | **Припущення:** для живих акаунтів показуємо поточний DisplayName; snapshot використовується, коли акаунт видалено. Підтвердити — OQ-06 |
| **P-09** | Refresh rotation | Дві вкладки одночасно викликають refresh → друга «повторно використає» токен → хибний спрацьовує reuse-detection | Reuse detection (відкликати всю *family*) + **grace window 10–30 с** для щойно ротованого токена |
| **P-10** | SignalR-дизайн | Token у query-string потрапляє в логи; довга WS-сесія переживає термін JWT; один інстанс | Не логувати query для `/hubs/*`; `CloseOnAuthenticationExpiration = true`; документувати single-instance ліміт (масштаб → Redis backplane) |
| **P-11** | Resync | Редагування/видалення, пропущені офлайн, **не видно** за `Sequence` | `Message.UpdatedSequence` із того ж лічильника → `GET messages?afterSequence=` повертає нові **та** змінені |
| **P-12** | Free-tier sleep | Безкоштовні web-сервіси засинають (Render — після 15 хв); WS-з’єднання рвуться, cold start ≈ 50 с | UI-стан «сервер прокидається», auto-reconnect, uptime-пінг, пояснення в README |
| **P-13** | Унікальність direct-чату | Гонка двох `POST` створить дві розмови | Унікальний індекс `DirectKey = "{minId}:{maxId}"` + get-or-create з retry при unique violation |
| **P-14** | Видалення повідомлення | «Soft delete» без очищення тексту = текст лишається в БД/бекапах | Tombstone: **обнулити `Body`** і видалити `MessageEditHistory`; рядок і `Sequence` лишаються |
| **P-15** | Видалення акаунта | Власник групи видаляється; email лишається в БД | Анонімізувати email/username (`deleted-{id}`), передати ownership найстаршому адміну/учаснику, група без учасників → soft delete |
| **P-16** | Repository + UoW поверх EF | `DbContext` уже є UoW; репозиторії для *читання* дублюють проєкції | Команди: репозиторії + `IUnitOfWork` (як ви хочете). **Запити (CQRS read side):** прямі `AsNoTracking`-проєкції через `IApplicationDbContext` |
| **P-17** | Пошук і приватність | Пошук не має показувати повідомлення до `VisibleFromSequence`, після clear чи видалені | Обов’язковий фільтр видимості в запиті + тест на це |
| **P-18** | OAuth | Автопрілінкування за email — вектор захоплення акаунта | Лінкувати за `(provider, sub)`; автозлиття за email — лише якщо провайдер підтверджує email **і** локальний email підтверджений; інакше — логін і лінкування в налаштуваннях. OAuth-юзеру потрібен онбординг «обери username» |
| **P-19** | 400 vs 422 | ASP.NET за замовчуванням повертає 400 для помилок моделі | Налаштувати 422 + `ValidationProblemDetails` (вимога лаби) |
| **P-20** | Rate limit за IP за проксі | Без `ForwardedHeaders` усі клієнти мають IP проксі Render → один спільний ліміт | `UseForwardedHeaders` + довіра до проксі платформи |

## 6. Функціональні вимоги

Пріоритети: **M** = MUST (потрібно для цілісності та Advanced-рівнів), **S** = SHOULD, **C** = COULD.
Колонка «Lab»: L1/L21 — яку лабу закриває.

### 6.1 Автентифікація та сесії (AUTH)

| ID | Вимога | Пр. | Lab |
|---|---|---|---|
| AUTH-01 | Реєстрація: email, password, username, displayName. Дублікат email → нейтральна відповідь (без user enumeration) | M | L21 |
| AUTH-02 | Пароль хешується **BCrypt (enhanced, work factor ≥ 11) або Argon2id** з унікальною сіллю; мін. довжина 10, макс. 72 байти для bcrypt; ніколи не логується | M | L1, L21 |
| AUTH-03 | Email verification **обов’язкова** до першого логіну; токен одноразовий, TTL 24 год, у БД лише хеш; повторна відправка з rate limit | M | L21 |
| AUTH-04 | Login (email+password) → короткоживучий JWT access token (10–15 хв) + refresh-cookie | M | L21 |
| AUTH-05 | Refresh: HttpOnly+Secure cookie, окрема таблиця `RefreshTokens`, **rotation + reuse detection** (див. P-09) | M | L21 |
| AUTH-06 | Logout відкликає **поточну** refresh-сесію | M | L21 |
| AUTH-07 | Password reset: email + одноразовий токен (TTL 30–60 хв); **відкликає всі** refresh-сесії | M | L21 |

| AUTH-09 | OAuth/OIDC (Google, GitHub) через Authorization Code flow; політика лінкування — P-18 | S | L21 |
| AUTH-10 | Захист від brute force: rate limit + тимчасовий lockout після N невдалих спроб | M | L21 |
| AUTH-11 | Список активних сесій і відкликання окремої | C | L21 |
| AUTH-12 | Невірний пароль → **401** із загальним повідомленням; неавторизований запит → 401; чужий ресурс → 403/404 | M | L21 |

### 6.2 Користувачі (USR)

| ID | Вимога | Пр. | Lab |
|---|---|---|---|
| USR-01 | `UserId` (GUID v7) — стабільний ідентифікатор; username ніколи не є ID | M | L1 |

## 10. «Make it yours» (обов’язковий твіст)

Лаба вимагає **один** твіст і його захист. Варіанти, що добре лягають на архітектуру:

| Варіант | Суть | Що змінюється в продукті |
|---|---|---|
| **A. Спільнота** — «чат вашої команди / групи / гуртожитку» | Реальні користувачі з першого дня | Тематичні дефолти, welcome-повідомлення, реальні дані для демо |
| **B. Тема** — «IRC-90s» (зелене на чорному, моноширинний) або «paper & pen» | Візуальна ідентичність | Тільки клієнт (дуже дешево) |
| **C. Обмеження** — авто-видалення через 24 год або ліміт 50 символів | Продуктове правило | Одне правило в Domain + фоновий cleanup (**обережно:** cleanup не має будити Neon щохвилини) |
| **D. Домен (авіація)** — ACARS-подібний месенджер льотної школи: інструктор ↔ курсант, структуровані типи повідомлень (`/briefing`, `/debrief`) | Прив’язка до вашого інституту | Типи повідомлень, шаблони, тематичний UI |

**Рекомендація:** **B + A** (тема + реальна спільнота) — найдешевше по обсягу і найкраще виглядає на демо. Якщо хочете сильніший «сюжет» для захисту — **D**. Рішення — OQ-04.
